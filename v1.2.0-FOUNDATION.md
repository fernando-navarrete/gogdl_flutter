# v1.2.0 — Foundation: tests, CI and CD

Work plan for the `v1.2.0` entry in [ROADMAP.md](ROADMAP.md). The goal is to make the bridge
testable and gated before any feature work (`v1.3.0`+) starts, so everything after it lands with
tests and a pipeline. No change to the Dart API or to the events Dart sees, so Lumen can move to
`v1.2.0` without touching its code.

GAPS items closed by this release: §1 (example app), §4 (progress coalescing, clippy/fmt),
§6 P0 (no tests), §6 (no CI, codegen drift, no release pipeline). The follow-up patches
(`v1.2.1`–`v1.2.4`) are listed at the end and are **not** part of this plan.

Tick each checkbox as it's done, one commit per phase (or smaller).

## Branch

All work happens on a new branch, created from `main` before Phase 0:

```sh
git switch main
git pull
git switch -c feat/v1.2.0-foundation
```

- Commit per phase (or smaller). Don't commit to `main` directly.
- Push the branch to `origin` so the CI jobs from Phase 5 can be run manually on it.
- When every phase is done and the pipeline is green on the branch, merge into `main`, then tag
  `v1.2.0` on `main` (Phase 7).

## Phase 2 — Extract the progress translators

GAPS §4 "The progress coalescing is untestable and duplicated". This is a pure refactor: the
progress events Dart receives must not change (same variants, same order, same coalescing).

- [ ] Add a module per job's translator under `rust/src/` (outside `api/`, so frb doesn't pick them up
  for codegen), e.g. `progress/{download,repair,verify,proton,saves}.rs`.
- [ ] Each translator is a plain state machine with no I/O:
  - `on_event(event) -> Vec<Progress>`: immediate emits (stage changes, per-path events).
  - `on_tick() -> Vec<Progress>`: coalesced emits (byte counters), only when dirty.
  - `finish() -> Vec<Progress>`: the final flush before `Finished`.
- [ ] Share one generic tick loop (`select!` over the event receiver and a 150ms interval) that drives
  any translator and writes to the `StreamSink`. The six job methods in `gogdl.rs` shrink to
  "start the `gogdl-lib` job, run the loop".
- [ ] Download and repair share their stage handling (one shared type or helper), keeping repair's
  separate allocation/verification path sets and its compressed-size lookup for `DownloadStarted`.
- [ ] Keep `let _ = sink.add(...)` behavior as it is. Stopping on a failed `sink.add` is `v1.3.0`.
- [ ] Do it one job at a time (one commit each), starting with the simplest (`verify_download`),
  and run Lumen against the branch after download/repair to check progress still looks right.

**Done when:** `gogdl.rs` has no inlined tick loops, the crate builds, clippy is clean, and a manual
download, repair, verify, Proton download and save sync in Lumen show the same progress as before.

## Phase 3 — Rust unit tests

GAPS §6 P0 "No tests at all".

- [ ] Enable `tokio`'s `test-util` feature under `[dev-dependencies]` (the `full` feature doesn't
  include it) so tests can use `tokio::time::pause`/`advance`.
- [ ] Translator tests, driven by synthetic `gogdl-lib` events, covering:
  - stage transitions and the final flush at each stage boundary;
  - one event per path (dedupe), including repair's separate allocation and verification sets;
  - `ProgressRegression` saturation (counters never go backwards or underflow);
  - repair's compressed-size lookup for `DownloadStarted`;
  - the saves per-file byte counters;
  - the final flush arriving before `Finished`;
  - the shared tick loop: coalescing within a tick, no emit when nothing changed.
- [ ] Model adapter tests for `GameBuild`, `DownloadableProduct` and `ProtonRelease`, built from JSON
  fixtures in `rust/tests/fixtures/` (or inline). If the `gogdl-lib` types can't be built from
  outside the crate, file GAPS §7.1 upstream, mark the tests `#[ignore]` with a pointer to it, and
  move on.

**Done when:** `cargo test` passes and covers every bullet above (or the adapter tests are skipped
with an upstream request filed).

## Phase 5 — CI (GitLab, self-hosted runner)

GAPS §6 "No CI". Reuse Lumen's `.gitlab-ci.yml` setup: Debian image, Flutter cloned at the
`.fvmrc` tag into a cached `.ci/flutter/`, `gogdl-lib` over SSH with a base64 deploy key, and the
runner's `extra_hosts` entry for `thinkcentre.home`.

- [ ] Add a read-only deploy key for `gogdl-lib` and store it as a masked, **unprotected** variable
  (Lumen's devlog: a protected variable comes through empty on unprotected branches).
  Configure cargo to use the SSH agent for git fetches (`CARGO_NET_GIT_FETCH_WITH_CLI=true`).
- [ ] Cache `~/.cargo/registry`, `~/.cargo/git` and `rust/target` keyed on `rust/Cargo.lock`.
- [ ] Jobs:
  - `rust`: `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`.
  - `dart`: `flutter analyze --fatal-infos` in the root and in `example/`.
  - `codegen`: install frb codegen `2.13.0`, run `flutter_rust_bridge_codegen generate`, fail on
    `git diff --exit-code`.
  - `integration`: install the Linux desktop build deps (clang, cmake, ninja, pkg-config,
    GTK 3 dev, xvfb), build the example for Linux, run the integration test under `xvfb-run`.
- [ ] Trigger policy: tags only (same as Lumen), plus manual runs on branches
  (`$CI_PIPELINE_SOURCE == "web"`).
- [ ] Check the pipeline actually goes red: push a throwaway failing Rust test and a failing Dart lint
  on a scratch branch, run it manually, then delete the scratch branch.

**Done when:** a manual pipeline on `feat/v1.2.0-foundation` passes all four jobs, and the red check
has been done.

## Phase 6 — CD (release on tag)

GAPS §6 "No release pipeline" (the version check and release; precompiled binaries are `v1.2.1`).

- [ ] A `release` stage that runs only on `vX.Y.Z` tags, after the check jobs:
  - fail unless `pubspec.yaml`'s `version:`, `rust/Cargo.toml`'s `version` and the tag (minus the
    `v`) are all equal;
  - extract that version's section from `CHANGELOG.md` and create a GitLab release with it
    (`release-cli` or the `release:` keyword).
- [ ] Make the changelog extraction fail if the section is missing, so a tag can't ship without notes.
- [ ] Test the version check against a scratch tag on a scratch commit with a mismatched version, then
  delete the tag.

**Done when:** the version mismatch fails the pipeline, and a matching scratch tag produces a
release with the right notes (delete it afterwards).
