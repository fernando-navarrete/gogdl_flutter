# v1.2.0 — Foundation: tests, CI and CD

Work plan for the `v1.2.0` entry in [ROADMAP.md](ROADMAP.md). The goal is to make the bridge
testable and gated before any feature work (`v1.3.0`+) starts, so everything after it lands with
tests and a pipeline. No change to the Dart API or to the events Dart sees, so Lumen can move to
`v1.2.0` without touching its code.

The plan covers `v1.2.0` and its four follow-up patches (`v1.2.1`–`v1.2.4`, under **Patches**).
The branch goes into `main` only after `v1.2.4`. The plan is then condensed into
`devlog/v1.2.0-foundation.md` and deleted (see **After `v1.2.4`**), as Lumen did for its `v1.1.0`
and `v1.2.0`.

GAPS items closed by `v1.2.0`: §1 (example app), §4 (progress coalescing, clippy/fmt), §6 P0 (no
tests), §6 (no CI, codegen drift, the version check and release of "No release pipeline"). Closed
by the patches: §6 "Built with the vendored cargokit" (a new item, added and closed by `v1.2.1`),
"Template leftovers", "Declared platforms are never built", "Tighten lints". The precompiled
binaries part of "No release pipeline" was planned for `v1.2.1` on cargokit. Native Assets has no
precompiled-binary support, so it's deferred to `v1.5.0` (see P1).

Tick each checkbox as it's done, one commit per phase (or smaller).

## Branch

All work happens on a new branch, created from `main` before Phase 0:

```sh
git switch main
git pull
git switch -c feat/v1.2.0-foundation
```

- Commit per phase (or smaller). Don't commit to `main` directly.
- Push the branch to `origin` so the CI jobs from Phase 5 can be run manually on it.
- Every tag (`v1.2.0` … `v1.2.4`) goes on a `feat/v1.2.0-foundation` commit. Tag pipelines run
  from the tag, so CI/CD and Lumen's pin don't need `main`.

  tag's commit ends up in `main`'s history. No merge commit and no re-tagging.

## Phase 2 — Extract the progress translators

GAPS §4 "The progress coalescing is untestable and duplicated". This is a pure refactor: the
progress events Dart receives must not change (same variants, same order, same coalescing).

- [x] Add a module per job's translator under `rust/src/` (outside `api/`, so frb doesn't pick them up
  for codegen), e.g. `progress/{download,repair,verify,proton,saves}.rs`.
- [x] Each translator is a plain state machine with no I/O:
  - `on_event(event) -> Vec<Progress>`: immediate emits (stage changes, per-path events).
  - `on_tick() -> Vec<Progress>`: coalesced emits (byte counters), only when dirty.
  - `finish() -> Vec<Progress>`: the final flush before `Finished`.
- [x] Share one generic tick loop (`select!` over the event receiver and a 150ms interval) that drives
  any translator and writes to the `StreamSink`. The six job methods in `gogdl.rs` shrink to
  "start the `gogdl-lib` job, run the loop".
- [x] Download and repair share their stage handling (one shared type or helper), keeping repair's
  separate allocation/verification path sets and its compressed-size lookup for `DownloadStarted`.
- [x] Keep `let _ = sink.add(...)` behavior as it is. Stopping on a failed `sink.add` is `v1.3.0`.
- [x] Do it one job at a time (one commit each), starting with the simplest (`verify_download`),
  and run Lumen against the branch after download/repair to check progress still looks right.

**Done when:** `gogdl.rs` has no inlined tick loops, the crate builds, clippy is clean, and a manual
download, repair, verify, Proton download and save sync in Lumen show the same progress as before.

### P1 — `v1.2.1`: migrate from cargokit to Native Assets

A new GAPS §6 item, "Built with the vendored cargokit" (add it in this patch, then tick it). The
crate is built by a vendored copy of cargokit (`cargokit/`, ~30 files) that each platform's
CMake, Gradle and podspec files hook into. frb now offers Native Assets in its place
([integration](https://cjycode.com/flutter_rust_bridge/manual/integrate/native-assets),
[migration](https://cjycode.com/flutter_rust_bridge/manual/integrate/migrate-cargokit-to-native-assets)).
A Dart build hook (`hook/build.dart`, through `flutter_rust_bridge_hooks` and
`native_toolchain_rust`) runs cargo, and the library is bundled as a code asset. The Rust and Dart
APIs don't change, so Lumen needs no code change.

How it differs from cargokit:

- The toolchain must be pinned in a `rust-toolchain.toml` to a concrete version (not `stable`,
  `beta` or `nightly`), and the file must list the targets. cargokit asked rustup for `stable`,
  which is why the CI image installs a toolchain under that name (Phase 5).
- The package is no longer an `ffiPlugin` plugin. The root `android/`, `ios/`, `linux/`, `macos/`
  and `windows/` dirs only hold cargokit glue, so they go away along with it.
- There are no precompiled binaries. `native_toolchain_rust` (1.0.x) always builds with cargo. It
  has nothing like cargokit's download-and-verify-signature path, so the old P1 (a signed,
  prebuilt Linux `.so` on a LAN host) can't be done as planned. They're deferred to `v1.5.0` (see the precompiled binaries checkbox
  below).

- [x] Check the prerequisites:
  - Flutter `3.47.2` runs build hooks without an experiment flag (`flutter config` has no
    native-assets switch that needs turning on).
  - `flutter_rust_bridge_codegen` `2.13.0` has `integrate --integration-backend native-assets`
    (the docs need `>= 2.13.0-beta.2`).
  - Pin `flutter_rust_bridge_hooks` to `2.13.0`, to match the other frb pins.
- [x] Add `rust/rust-toolchain.toml`: `channel` set to the current stable (`1.98.1` locally),
  `components = ["rustfmt", "clippy"]` and `targets = ["x86_64-unknown-linux-gnu"]` only (other
  targets are P3's call). Check where `native_toolchain_rust` looks for the file (crate dir or
  package root), and put it there. The `rust` job also picks it up, so the pinned version might
  report new fmt or clippy findings. Fix them in the same commit.
- [x] On a clean tree, run `flutter_rust_bridge_codegen integrate --integration-backend native-assets`
  in the root and review the diff. Keep `hook/build.dart`, the new `pubspec.yaml` dependencies
  (`hooks`, `flutter_rust_bridge_hooks`) and any `flutter_rust_bridge.yaml` change. Revert anything
  that rewrites the crate, `lib/` or the template files (P2 handles those). `rust/Cargo.toml`
  already has `crate-type = ["cdylib", "staticlib"]`.
- [x] Remove cargokit:
  - the `cargokit/` dir;
  - the `plugin:` section of `pubspec.yaml`, with its `ffiPlugin` entries and template comments;
  - the root `android/`, `ios/`, `linux/`, `macos/` and `windows/` dirs;
  - the analyzer excludes for `cargokit/**` and those platform dirs;
  - `plugin_platform_interface`, if nothing uses it.

  Leave `example/`'s platform dirs to P3.
- [x] Run `flutter pub get`, `flutter_rust_bridge_codegen generate` and build_runner (Phase 4's
  commands). The generated loader may change the way `RustLib.init()` finds the library. Commit
  whatever gets regenerated, so the `codegen` job's no-diff check keeps passing. `RustLib.init()`

  - `ci/build-image.sh` adds the Rust version to the image tag. Update `image:` to match.
  - The `.toolchain` check also fails when `rustc --version` doesn't match the toml, the same as

  - `.gitlab-ci.yml`: fix the `integration` comment ("cargokit compiles the plugin"). The hook

  that `.so` in `v1.5.0` itself.
