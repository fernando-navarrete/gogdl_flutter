# Devlog — v1.3.0 Download management

Everything Lumen's `v1.3.0` download management stage needs from the bridge, from the `v1.3.0`
ROADMAP entry: stopping jobs when their listener goes away, request timeouts, error kinds, a cancel
handle, the resume path, and install size and free space. Ran as eight phases on 2026-09-25; kept
here for the decisions and pitfalls that aren't obvious from the diff. **Breaking** for Lumen: the
job methods take a `CancelToken` and each progress enum gained a `Cancelled` variant. The tag
pipeline was green. Adopting it (and the two end-to-end checks that need a GOG login) is Lumen's own
Phase 3, on its `release/v1.3.0` branch.

## Phase 0 — `gogdl-lib` `v1.2.3`

Upstream had shipped nearly everything the plan asked for in `v1.2.0`–`v1.2.3`, so the pin moved
from `v1.0.11` to `v1.2.3` first and the phases used the upstream API instead of workarounds. The one
item still open upstream (a revoked session vs a routine expiry, GAPS §7.3's auth part) is planned
for upstream `v1.5.0` and didn't block the release.

**Pitfall:** the bump broke the build. `v1.2.0` made the event and error enums `#[non_exhaustive]`,
so every translator `match` needed a `_ =>` arm, and `v1.2.3` deprecated `DownloadEvent::Preparing`/
`Prepared`, which fails `clippy -D warnings`. **Decision:** `Started { .. }` became the download
stage boundary in `download.rs` and `repair.rs` rather than `#[allow(deprecated)]`, since the old
events go away in upstream `v1.4.0`. The deprecated events fall into `_ =>`, with a test per
translator that they don't flush early.

Upstream chose a documented drop contract for cancellation (§7.2), not a token: dropping a job
future stops it and leaves state that `repair_game` can finish (game jobs), `path` untouched
(Proton, which now stages under a hidden directory), or the old or complete new save (saves). So
every cancel in the bridge is "drop the future".

## Phase 1 — Stop a job when its listener goes away

The plan was unsure whether cancelling a Dart subscription makes frb's `sink.add` fail. **It does:**
a throwaway Linux integration test on a Proton download saw every `add` after the cancel return
`Err`, while the job kept running. frb 2.13.0's `RustStreamSink` closes its `ReceivePort` in the
`async*` generator's `finally`, and posting to a closed port fails.

So all six jobs go through `progress::run(job, translator, rx, emit)`, which `select!`s the job
against `drive` and drops the job future once an emit fails. A job whose listener is gone returns
`Ok(())`, since there's nobody to report to. A failed final flush after the job has finished keeps
its result. The stop is noticed on the next emit (one 150ms tick), so a job that reports nothing
runs until it does; Phase 2's read timeout bounds that, and Phase 4's handle doesn't depend on it.

## Phase 2 — Request timeouts

`GogdlApi::new` builds its client in `rust/src/client.rs` (outside `api/`, so frb doesn't list it)
with a 10s `connect_timeout` and a 30s per-read `read_timeout`. **Decision:** no overall `timeout`,
which would kill a 500MB Proton tarball. `GogdlApi::new` stays sync and infallible, falling back to
`Client::new()` if the builder fails.

**Pitfall:** only `gogdl-lib`'s metadata fetches and game chunk downloads retry a timeout. The
Proton tarball, both saves transfers and `login_with_code` fail on the first one. Still better than
hanging; requested upstream as GAPS §7.11.

**Pitfall:** reqwest 0.13 starts `read_timeout` at `send()` and only restarts it on response-body
reads, so it covers the whole request-body upload: a save upload over 30s fails (about 4 MB on a
1 Mbit uplink). **Decision:** keep 30s, document it on `upload_save_files`, pin it down with a test,
and ask upstream (§7.11). `client.rs`'s tests use loopback servers and 200ms timeouts.

## Phase 3 — Error kinds

A flat `GogErrorKind` and a sync `GogError::kind()`, mapped in `rust/src/error_kind.rs` (outside
`api/`) with one function per upstream enum, walking the nested errors. Anything unmapped is
`unknown`, deliberately including 401s and other non-404 statuses, `ProductNotOwned` and extraction
errors. A revoked session is `unknown`, not `sessionExpired`, until upstream's §7.3 auth part.

**Decision:** the free-space numbers are exposed now as `space_shortfall() -> Option<SpaceShortfall>`
rather than left in `message()`. The fields are `required_bytes`/`available_bytes`, since `required`
is a Dart keyword. Lumen's D7 names map onto these kinds; `CHANGELOG.md` lists the mapping.

**Pitfall:** Phase 1's flush-order test failed about one run in four: its job slept exactly one tick,
so the tick and the second event were ready at the same paused instant and `select!` picked either.
It now sleeps 1.5 ticks.

## Phase 4 — Cancel handle

**Decision:** Dart creates an opaque `CancelToken` (Lumen's name) and passes it to each job method,
instead of a job id plus a map on `GogdlApi`. It wraps `tokio_util`'s `CancellationToken`, which was
already in the lock file. The methods take `&CancelToken`, which frb decodes under a shared read
lock, so a sync `cancel()` during the job isn't blocked.

**Decision:** a cancel reaches Dart in-band (Lumen's D2), not as `Err(GogError::Cancelled)`: each
of the six progress enums got a `Cancelled` variant, sent last after `drive` flushes what it has,
then the method returns `Ok(())`. Lumen's exhaustive `switch`es fail to compile until they handle
it, and cancels stay off `guardBridgeStream`'s error path. Phase 3's `GogError::Cancelled` and
`GogErrorKind::cancelled` were removed, since nothing produced them any more.

The cancel covers the whole method body: pre-job fetches (`get_product_bundles`,
`get_proton_release_by_tag`) run under `run_until_cancelled`, so a cancel there writes nothing.
`progress::run` returns `Outcome::{Finished, Cancelled, ListenerGone}`, boxes the job so a cancel can
drop it while `drive` keeps draining, and is biased towards the job's output, so a cancel that races
a finished job is a no-op. A job that's already cancelled is never polled.

**Pitfall:** Proton's extraction runs in a `spawn_blocking` that holds an event sender for a while
after its job future is dropped, so waiting for every sender to drop hung the cancel. On a cancel,
`drive` closes `rx` instead.

**Pitfall:** `lib/gogdl_flutter.dart` exports with `show` lists, so new generated types aren't
exported until added by hand. Phase 3 had missed `GogErrorKind` and `SpaceShortfall`; they went in
with `CancelToken` and the six `*_Cancelled` classes (and Phase 6 hit it again).

A throwaway Proton integration test ended the stream with `Cancelled` 2ms after `cancel()`, with
`path` left empty.

## Phase 5 — Resume path

**Decision:** document only, no `resume_download` alias. Lumen already wraps `repair_game` as its
resume call, so an alias would add a second name without improving a call site. `downloadGame` says
it always starts over (skipping what's on disk is upstream `v1.3.0`, not pinned here), and
`repairGame` says it's the resume path and only reads what was already on disk (`gogdl-lib`
`v1.2.1`).

## Phase 6 — Install size and free space

`get_install_size` builds on upstream's `get_product_sizes` (build metadata, no manifest fetches)
rather than `get_product_bundles`, which Lumen's D3 had assumed; upstream guarantees the sums are
equal. It returns totals plus per-product sizes (a superset of D3), and matches products the way
`get_product_bundles` does: a non-`i32` id is never selected, duplicates count once, and ids not in
the build are ignored. `get_free_space` is an async wrapper over upstream's, the same figure the
download's own check uses. The doc comments say Lumen's check is a warning, not a guarantee, since a
partly installed game needs less than `disk_bytes`.

The free-space test on a missing child of the temp dir allows 64 MiB of slack against the temp dir's
own figure, since other processes write in between.

## Phase 7 — Release `v1.3.0`

Tagged on the feature branch like `v1.2.0`, with both version bumps and both lock files in one
commit. The example app needed no change (it only calls `getLoginLink()`). The two end-to-end checks
that need a GOG login (game download → cancel → `repair_game`, and `getInstallSize` in the install
dialog) moved to Lumen's adoption.
