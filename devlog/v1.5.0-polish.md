# Devlog — v1.5.0 Polish and API cleanup

What Lumen's `v1.5.0` stage needed from the bridge: login error kinds (its D1) and the breaking
cleanup (its D3). Its D2, a precompiled `.so`, was dropped by Lumen's Phase 0 (it ships an AppImage
built from source), so it isn't here. Ran as steps 0–13 in five MRs on 2026-10-16 and 17, ending in
one tag, `v1.5.0`. **Breaking**: Lumen adopts it in its Phase 7, working from the `CHANGELOG.md`
entry. The tag pipeline was green, including `release` and `tool/check_lib_pin.sh`, and the GitHub
mirror has the tag. There is no `v1.5.1`: the progress channels measured bounded (Step 12). The work
plan was deleted with this devlog. Kept here for the decisions and pitfalls that aren't obvious from
the diff.

## MR 1 — Pin `gogdl-lib` `v1.4.3`

Pinned at `ca89691`, from the GitHub mirror. The bump broke what upstream's devlog said it would
(13 errors in `error_kind.rs`, four in the download and repair translator tests, and the
`repair_game` call under `clippy -D warnings`), and changed no Dart signature: codegen showed no diff
in `lib/src/rust/`. `rust/deny.toml` lost its `licenses.clarify` entry for `gogdl-lib`, since the tag
has the `license` field it was waiting for.

**D2 — `repairGame` stays.** It calls upstream's `download_game` with the same bundles, path and
sender, so `RepairTranslator` and `RepairGameProgress` are untouched and Lumen's resume path doesn't
change. Its explanation is a plain `//` comment, not a `///` one, so this MR changed no Dart docs.
Whether it stays past `v1.6.0` is open, when upstream removes its own method.

`GogError::SavesError` is gone: upstream's saves methods return `GogDlError`, so `kind()` reaches the
saves mapping through the main match. `GogError` is opaque in Dart, so nothing shows there.

## MR 2 — Login kinds and API cleanup

**D1 — a revoked session is `sessionExpired`.** Lumen reacts the same way to both (sign in again) and
already had the case, so only `invalidLoginCode` is new. `message()` keeps GOG's description.

**D3 — `ProductType` is `game`, `dlc` or `other`**, compared case-insensitively: real responses say
`"GAME"`, upstream's fixtures say `"dlc"`. `other` loses the raw string, but a pack or a type GOG adds
later doesn't fail the call.

`FileNotFound`, `ChecksumMismatch` and `CouldNotResolvePath` all carry the first failing chunk's
uncompressed size, not the file's, so the field is `chunk_size` in all three.

**Pitfall (avoided this time):** `ProductType` went into `lib/gogdl_flutter.dart`'s `show` list in the
same commit as the type. It was the `v1.3.0` and `v1.4.0` trap. Removing the three getters also let
`#[allow(deprecated)]` go from `mod frb_generated`.

The example's integration test ran on the desktop display, since `xvfb` isn't installed here.

## Step 5 — Login kinds against GOG

A throwaway Dart probe in `example/`, not committed.

- A truncated code is `invalidLoginCode`. So is a code retried about ten minutes after its first
  exchange ("The authorization code has expired"). Network off is `network`. A garbage refresh token
  is `sessionExpired`.
- **Pitfall:** a code exchanged a second time right after the first is **accepted**: GOG has a grace
  window, so "already used" isn't rejected at once. A real refresh token that was rotated also keeps
  working when the old one is restored. A never-used code left 10+ minutes wasn't tested on its own.
- **Gap:** a garbage access token with `valid_until` in the future makes `getOwnedGames` fail as
  `unknown`. `embed.gog.com/user/data/games` answers a bad bearer with a 302 to an HTML login page,
  not a 401, so upstream's refresh-on-401 never runs. It only matters if GOG kills an access token
  early. Filed as GAPS §7.14.

## Step 12 — Bounded progress channels (D4)

Buffer map: upstream's `UnboundedSender` (fixed by its signatures) → `progress::drive` (drains it
continuously, never waits on Dart, one coalesced emit per 150 ms tick) → `StreamSink::add` →
allo-isolate's `Dart_PostCObject` (non-blocking, queues in the VM port). Immediate emits are
deduplicated per path. The sink gives no backpressure signal, so dropping superseded updates would
have needed a Dart-side ack.

Measured with a probe that blocked the Dart isolate for 30 s on the first progress event (Linux debug
build, The Witcher 3, `1495134320`, 60 GB, 1745 files, RSS from `/proc/self/status`):

- **Download, stalled:** 270 MB before, 370 MB after the stall, 480 MB peak, 454 MB at the end;
  249 messages in the burst. **Baseline:** 391 MB at 30 s, 493 MB peak, 448 MB at the end. The stall
  costs nothing; the growth is the download itself.
- **Verify, every file corrupted** (17028 bad chunks in 1745 files), stalled: 268 MB before, 295 MB
  after, 302 MB at the end; 1948 messages in the burst, 1745 of them `checksumMismatch` (one per
  file). **Baseline:** 304 MB at 30 s, 305 MB at the end.

Bounded: growth while stalled is one small message per tick plus one per bad file. GAPS §5 is closed
with these numbers, and no `v1.5.1` was tagged.

**Found on the way, not investigated:** `downloadGame` and `verifyDownload` with a `buildName` that
doesn't exist (a build id instead of the version name) end the stream after about 10 ms with no event
and no error, while `getDownloadableProducts` fails with `notFound`. Written up in GAPS §1.
