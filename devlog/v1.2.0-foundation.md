# Devlog — v1.2.0 Foundation

Tests, CI and CD from the `v1.2.0` ROADMAP entry, plus the `v1.2.1`–`v1.2.4` follow-up patches. Ran
as eight phases and four patches over 2026-09-24/25; kept here for the decisions and pitfalls that
aren't obvious from the diff. No change to the Dart API or to the events Dart sees at any point, so
Lumen only ever had to move its pin. Ended with every tag's pipeline green.

## Phase 0 — Green baseline

`cargo fmt` only drifted in `rust/src/frb_generated.rs` (edition 2024 import ordering vs. frb's
output). **Decision:** mark `mod frb_generated;` `#[rustfmt::skip]` rather than reformat it, since
every regenerate would undo the formatting and break Phase 4's no-diff check. Landed as its own
commit. The clippy warning was a redundant closure.

## Phase 1 — Example app and integration test

The example is now a minimal offline smoke app (`RustLib.init()`, construct `GogdlApi`, show
`getLoginLink()`), and the integration test asserts the same. Nothing touches the network, so it
can run anywhere CI can open a display. `test_driver/` and the root's unused `integration_test`
dev-dependency were removed.

## Phase 2 — Progress translators

Pure refactor. Each job's progress logic became a plain state machine (`on_event` / `on_tick` /
`finish`) under `rust/src/progress/`, deliberately outside `api/` so frb doesn't try to generate
bindings for it. One shared tick loop (`select!` over the event receiver and a 150ms interval)
drives all six jobs, and download and repair share their install stages while keeping repair's
separate allocation/verification path sets and its compressed-size lookup.

One job per commit, simplest (`verify_download`) first, so a regression in Lumen's progress display
could be bisected to a single job. `let _ = sink.add(...)` was left as it was: stopping a job when
its listener goes away is `v1.3.0`.

## Phase 3 — Rust unit tests

**Pitfall:** `tokio`'s `test-util` feature (for `time::pause`/`advance`) isn't part of `full`, so it
goes under `[dev-dependencies]`. The progress enums also needed test-only derives to assert on.

The plan expected `gogdl-lib`'s types might not be constructible from outside the crate (which
would have meant filing GAPS §7.1). They all deserialize, so the model adapter tests use inline
JSON fixtures and nothing was filed.

## Phase 4 — Codegen check

**Pitfall:** without a root `build.yaml`, build_runner's freezed step walks the Flutter SDK inside
the repo (`.fvm`, `.ci/flutter`) and the example's plugin symlinks back to the repo root, taking
minutes and reporting "Failed to build". `build.yaml` limits it to `lib/**`.

**Pitfall:** `flutter_rust_bridge_codegen generate` runs its own build_runner pass, which can delete
the six `*.freezed.dart` files without rewriting them ("skipped, wrote 0 outputs"). So the codegen
check runs an explicit `dart run build_runner build --delete-conflicting-outputs` after it, and
only then checks for a diff. `flutter_rust_bridge.yaml`'s `dart_output` was already right; the plan
had a typo.

## Phase 5 — CI

Reused Lumen's setup: base64 deploy key for `gogdl-lib` in a masked, **unprotected** variable (the
protected-variable-comes-through-empty pitfall from Lumen's `v1.1.0` devlog), and
`CARGO_NET_GIT_FETCH_WITH_CLI=true` so cargo uses the ssh-agent. The `codegen` job's diff check is
split into `git diff --exit-code` and a `git status --porcelain` test so an untracked or deleted
generated file can't mask drift. Confirmed the pipeline goes red with a throwaway failing Rust test
and Dart lint on a scratch branch.

**Decision:** a prebuilt CI image, added after the first pipelines on a slow network and a small
runner. Installing apt packages, rustup, the frb codegen and Flutter per job was too slow, so
`ci/Dockerfile` bakes them in. The runner uses docker-in-docker, so jobs can't see the host's
images: `ci/build-image.sh --load-into <container>` builds on the host and loads the image into
the runner's daemon, and jobs use `pull_policy: if-not-present`. A `.toolchain` check fails a job
whose image has a stale Flutter (and, since `v1.2.1`, a stale Rust). Rebuild the image after
bumping `.fvmrc`, the frb version or `rust-toolchain.toml`.

## Phase 6 — CD

The `release` stage runs only on `vX.Y.Z` tags, after the checks, and fails unless `pubspec.yaml`,
`rust/Cargo.toml` and the tag agree, then creates a GitLab release from that version's
`CHANGELOG.md` section (failing if the section is missing).

**Pitfall:** found with the `v1.1.99` scratch tag: a version bump that leaves `rust/Cargo.lock` or
`example/pubspec.lock` stale fails `rust` under `--locked` and `codegen` on its diff check, so the
gate checks both lock files' entries for this package too (`tool/release_notes.sh`).

**Pitfall:** the `release` job couldn't reach `https://thinkcentre.home` until it trusted the
runner's CA. It appends `CI_SERVER_TLS_CA_FILE`, which the runner provides when `tls-ca-file` is
set in its `config.toml`. Mismatch failed the pipeline and the matching scratch tag produced a
release with the right notes; both were deleted afterwards.

## Phase 7 — Release `v1.2.0`

Tagged on the feature branch, not `main`: tag pipelines run from the tag, so neither CI/CD nor
Lumen's pin needed `main`. Lumen built against it with no change.

## P1 — `v1.2.1`: cargokit to Native Assets

Replaced the vendored cargokit (~30 files plus per-platform CMake/Gradle/podspec glue) with a Dart
build hook (`hook/build.dart`, through `flutter_rust_bridge_hooks` pinned to `2.13.0`). The package
is no longer an `ffiPlugin`, so the root `android/`, `ios/`, `linux/`, `macos/` and `windows/` dirs
went with it. `RustLib.init()` with no arguments still works, and `libgogdl_flutter.so` still lands
in the bundle's `lib/`, which Lumen's packaging relies on.

Native Assets requires a concrete toolchain version in a `rust-toolchain.toml`, so it's pinned to
`1.98.1` with `rustfmt`, `clippy` and only the `x86_64-unknown-linux-gnu` target. The CI image
installs that version instead of a toolchain named `stable` (which was only there because cargokit
asked for it). The hook's cargo needed git and toolchain setup provided through files rather than
environment variables in CI.

**Decision:** precompiled binaries are deferred to `v1.5.0`. `native_toolchain_rust` always builds
with cargo and has nothing like cargokit's download-and-verify path. The alternative, a custom hook
that downloads a signed prebuilt `.so` and falls back to the frb builder, was rejected because it
means reimplementing cargokit's artifact provider (crate hash, ed25519 check, hosting, and the
runner-CA TLS issue from Phase 6), which is more than one session. `v1.5.0` needs a prebuilt `.so`
for Lumen's AppImage/Flatpak packaging anyway, so it gets built and published there.

## P2 — `v1.2.2`: template leftovers

Real README (what the bridge is, the LAN-only `gogdl-lib` dependency, how it's built, regenerating
bindings, CI and releases), the template `0.0.1` changelog entry replaced by a `1.0.0`–`1.1.3`
backfill from the tags, a real `pubspec.yaml` description, `publish_to: none`, and the unused `ffi`
and `ffigen` dev-dependencies dropped.

## P3 — `v1.2.3`: Linux only

**Decision:** option (a). Lumen is the only consumer and needs Proton, so nothing but Linux is built
or declared. The example's `android/`, `ios/`, `macos/` and `windows/` dirs went, and frb's web
output stopped being generated (`web: false`), which also removed the wasm section of
`frb_generated.rs`. The `codegen` job still shows no diff.

## P4 — `v1.2.4`: Dart lints

`strict-casts`, `strict-inference` and `strict-raw-types`, plus rules for unawaited futures, missing
types, `dynamic` calls, unclosed streams and subscriptions, single quotes, `final` locals and sorted
directives/dependencies, on top of `flutter_lints`. Generated code (`lib/src/rust/**`,
`*.freezed.dart`) is excluded so a regenerate never trips a lint and the codegen check stays
meaningful. `example/` inherits the root config.
