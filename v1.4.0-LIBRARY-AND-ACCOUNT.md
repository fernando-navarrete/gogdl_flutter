# v1.4.0 — Library and account

Work plan for the `v1.4.0` entry in [ROADMAP.md](ROADMAP.md), split into small tasks, each one MR
(or one upstream request). The goal is the two things Lumen's `v1.4.0` work plan
(`../lumen/v1.4.0-LIBRARY.md`, "Dependency changes") asks the bridge for: `clearCache()` (its D3)
and `removeProducts()` (its D1). Both are **[lib]**, so `gogdl-lib` ships them first. It's **not
breaking**: everything is added. It's tagged before Lumen's **Phase 6** (adopt the new bridge), not
before its stage, since Lumen's Phases 1–4 need nothing from here. (They weren't done when T5 ran, so T5 used a probe instead of Lumen.)

GAPS items closed by `v1.4.0`: §2 "No way to refresh cached library data" and "Remove a product's
files from an install", and §6 CI/CD "`tool/check_lib_pin.sh` hasn't run in a tag pipeline yet"
(the tag is its first real run). The follow-up patches close §1 (both `get_proton_releases` items
and `get_downloadable_products` failing on one lookup), §3 (boxart and background fetched
separately) and §5 (serial product details).

Tick each checkbox as it's done.

## Workflow

`main` and the `v*` tags are protected (README "CI and releases"), so the `v1.3.0` plan's single
long-lived feature branch doesn't apply any more:

- One branch and one squash MR per task, into `main`. Everything here is additive, so a merged
  task that isn't tagged yet breaks nothing.
- Open MRs with push options (`-o merge_request.create -o merge_request.target=main -o
  "merge_request.title=..." -o merge_request.remove_source_branch`), not `glab`. Check the title
  and squash message in the merge widget.
- Tags only go on `main`, after a `release/vX.Y.Z` MR merges.
- If Lumen needs a task before the tag (for the end-to-end check in T5), it pins `ref:` to the
  merged commit on `main` on its own branch, per the CI/CD devlog's D2.

- **Decided: (b).** Upstream shipped both in its `v1.3.0`; this repo pins `v1.3.2` (T2).
- (a) **Recommended.** Both are additive, so upstream ships them as `v1.2.x` patches (`v1.2.4`

If (a), update ROADMAP's `v1.4.0` entry ("its `v1.3.0`, if that roadmap takes them") and add a
`v1.4.x` patch to pick up upstream `v1.3.0` later, since it changes behavior.

### What to ask for, beyond GAPS §7.12–7.13

- `clear_cache` must not corrupt an in-flight fetch: a fetch that started before the clear may
  repopulate the cache with its (current) result, but must not panic or leave a half-built entry.
  Sync or async is upstream's choice; the bridge exposes it as a `Future` either way.
- `remove_products`: an empty `remove` is a no-op that fetches nothing. An id in both `keep` and
  `remove` is an error (or is treated as kept; upstream decides, the bridge documents it). A path
  that would escape `path` after normalization is never deleted. Errors use existing variants
  where they fit (404 → `HttpError`, I/O → `FileSystemError`), so `error_kind.rs` maps them
  without a new `GogErrorKind`.
- A public result type that's test-constructible like the others (§7.1): a struct with
  `files_removed` and `bytes_freed`, deserializable from JSON or with public fields.

## Patches (`v1.4.1+`)

One task, one release MR and one tag each, same steps as T6. None blocks Lumen.

### P1 — `v1.4.1`: faster, tolerant `get_downloadable_products`

GAPS §1 "`get_downloadable_products` fails the whole call…", §5 "fetches product details serially".
Lumen measured 2.5 s for Alien: Isolation's 8 products.

- [x] Fetch details with `futures::stream::iter(...).buffered(N)` (order kept), N = 8 like Lumen's
  limiter.
- [x] **Decision D3 — A failed lookup.** (a) **Recommended:** drop that product and keep the rest,
  but fail the call if the `GAME` product's lookup fails (the DLC tab is meaningless without it).
  (b) Keep it with a placeholder name ("Product <id>"): Lumen would show an unnamed toggle. Either
  way the return type doesn't change, so it's a patch.
- [x] Tests: order kept, one failing DLC dropped, failing base game fails the call (a local
  server or a seam over the per-product fetch).
- [x] Time Alien: Isolation again and put the number in the changelog.

### P2 — `v1.4.2`: `getGameLinks()`

GAPS §3 "Boxart and background each fetch `get_game_links` separately".

- [ ] `get_game_links(game_id) -> GameLinks { boxart, background }`, one upstream call.
- [ ] Deprecate `get_game_boxart_link` and `get_background_image_link`. Check whether frb 2.13.0
  turns `#[deprecated]` into Dart's `@Deprecated`; if not, say it in the doc comment and in the
  changelog. Removal is `v1.5.0` (already in ROADMAP).

### P3 — `v1.4.3`: Proton pages

GAPS §1 "can't tell a filtered page from the end of the list" and "casts `i32` to `u32`".

- [ ] Changing `get_proton_releases`' return type would break Dart in a patch. Add
  `get_proton_release_page(page) -> ProtonReleasePage { releases, has_more }` instead, where
  `has_more` comes from the unfiltered page size (a full page of 5 means there may be more), and
  deprecate `get_proton_releases`. Add it to ROADMAP `v1.5.0`'s removals.
- [ ] A negative `page` fails instead of wrapping. With no bridge-own `GogError` variant and no
  new `GogErrorKind` allowed in a patch, add an opaque `GogError::InvalidArgument` whose `kind()`
  is `unknown` (opaque, so additive in Dart), or take `page` as `u32` in the new method only.
  Pick one in the MR; the old method gets the same check.
- [ ] Tests: a filtered-out full page reports `has_more`, a short page doesn't, negative page
  errors.
