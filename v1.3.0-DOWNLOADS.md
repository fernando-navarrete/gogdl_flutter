# v1.3.0 — Download management

Work plan for the `v1.3.0` entry in [ROADMAP.md](ROADMAP.md). The goal is everything Lumen's
`v1.3.0` download management stage needs from the bridge: stopping and cancelling jobs, the resume
path, error kinds Dart can switch on, install size and free space, and request timeouts. It's a
**breaking** release: job methods take a cancel handle and errors carry a kind, so it ships together
with the Lumen change that adopts it, and it's tagged **before** Lumen starts its `v1.3.0`.

GAPS items closed by `v1.3.0`: §1 (cancelling a stream doesn't stop the job, no request timeouts),
§2 (cancel and pause, structured errors for the downloads page, install and download size, free
space, resume an interrupted install). The login error kinds in §2 "Structured errors" stay open
for `v1.5.0`.

This release depends on `gogdl-lib` more than `v1.2.0` did. **Dependencies on `gogdl-lib`** lists
what's needed upstream, what works on the current pin in the meantime, and which bridge phase each
one affects. Following ROADMAP's rule, the upstream requests go out first (Phase 0), and nothing in
this plan waits on them.

Tick each checkbox as it's done, one commit per phase (or smaller).

## Branch

All work happens on a new branch, created from `main` before Phase 0:

```sh
git switch main
git pull
git switch -c feat/v1.3.0-downloads
```

- Commit per phase (or smaller). Don't commit to `main` directly.
- Push the branch to `origin` and run the pipeline manually on it after each phase.
- Every tag (`v1.3.0`, and any `v1.3.x` under **Patches**) goes on a `feat/v1.3.0-downloads`
  commit, as in `v1.2.0`. Tag pipelines run from the tag, so CI/CD and Lumen's pin don't need
  `main`.
- After the last tag (see **After `v1.3.0`**), merge into `main` with `git merge --ff-only`.

## Starting point

- `main` is at `e97fd98`. `pubspec.yaml` and `rust/Cargo.toml` are at `1.2.4`. Flutter `3.47.2`
  (`.fvmrc`), frb `2.13.0`, Rust `1.98.1` (`rust/rust-toolchain.toml`).
- `gogdl-lib` is pinned to `v1.0.11`, which is also its `HEAD`. Nothing in this plan needs a newer
  pin.
- `rust/src/api/gogdl.rs` is ~370 lines. The six jobs (`download_game`, `repair_game`,
  `verify_download`, `download_proton_release`, `download_save_files`, `upload_save_files`) each
  `tokio::join!` the `gogdl-lib` future with `progress::drive` and discard every `sink.add`
  result (`let _ = ...`).
- `GogError` is an opaque enum with two variants (`GogdlError(GogDlError)`,
  `SavesError(SavesError)`) and a single `message()`. Lumen matches on nothing: it shows
  `gogErrorText()` (`lumen/lib/common/gog_error.dart`).
- A job's `Result` doesn't reach Dart in-band. frb discards it for stream methods, and Lumen's
  `guardBridgeStream` (`lumen/lib/state/bridge_stream.dart`) catches it in a zone and re-injects it
  into the stream. A cancelled job's outcome goes through the same path.
- `GogdlApi::new` builds `Client::new()`, with no timeouts.
- `frb`'s `StreamSink::add` returns `Err(Rust2DartSendError)` only when posting to the Dart port
  fails. Whether cancelling the Dart subscription closes that port is **unverified** (Phase 1
  checks it first).

## Dependencies on `gogdl-lib`

What `v1.3.0` needs from `gogdl-lib` (GAPS §7.2–7.4, plus one new request), checked against
`gogdl-lib` `v1.0.11`. Upstream `GAPS.md` titles are quoted where it already tracks the item.
**None of them blocks the release.** Each has a fallback that ships in `v1.3.0`, and the upstream
fix is picked up later as its own `v1.3.x` patch (see **Patches**), per ROADMAP's rule that a
`gogdl-lib` bump that changes behavior gets its own tag.

| # | Request | Bridge phase | Fallback in `v1.3.0` |
|---|---|---|---|
| §7.2 | Cooperative cancellation / cancel-safe drop contract | 1, 4 | Drop the job future (works today, see below). Saves jobs aren't cancellable. |
| §7.3 | Structured, distinguishable errors | 3 | Coarse kinds from today's variants; the rest map to `unknown`. |
| §7.4 | Public free-space query | 6 | Bridge implements it with `statvfs`. |
| §7.6 (part) | Don't truncate a local save before the new one is on disk | 1, 4 | Saves jobs run to completion even when their listener goes. |
| new §7.10 | Per-product depot sizes without fetching every manifest | 6 | Sum sizes from `get_product_bundles` (slower, correct). |

### §7.2 — Cooperative cancellation

What's needed: a documented contract that dropping the future returned by `download_game`,
`repair_game`, `verify_files`, `download_proton_release` and the saves transfers is safe, and leaves
state that `repair_game` can resume. Or a `CancellationToken` parameter, if upstream prefers
explicit cancellation. Either works for the bridge, which only needs to stop the work.

What `v1.0.11` does today, from reading the code:

- No job uses `tokio::spawn`, so dropping the future stops all async work. The only detached work
  is `spawn_blocking`: the chunk MD5 in `downloader/util/hash.rs` (finishes its one chunk, then its
  result is discarded) and the Proton extraction task (sees EOF or a broken pipe once the download
  half is dropped, and stops).
- Game download and repair: files are preallocated (`set_len`), and chunks are written in place.
  A drop leaves partially written chunks, which `repair_game`'s MD5 verification catches and
  re-downloads. So "drop, then `repair_game`" is a correct resume today. It's slow, because of
  upstream's "`repair` checksums the chunks of files it has just allocated" and "`download`
  re-downloads every chunk regardless of what's already correct on disk" (performance only).
- Proton: a drop leaves a partially extracted tree under `path`, named after the tarball's root
  (not the sanitized tag), since the rename happens only after extraction. Re-downloading overlays
  it, per upstream's "Re-downloading a Proton release whose tarball root already matches its tag
  extracts over the old tree instead of replacing it". Lumen must treat a cancelled Proton download
  as leaving junk under `path`, until upstream stages extraction.
- Saves: a drop mid-write can leave a truncated save (see §7.6 below). This is why saves jobs are
  excluded from cancel and from the listener-gone stop in `v1.3.0`.

Ask upstream to state this contract in the rustdoc of each method (and fix the Proton staging), so
the bridge relies on documented behavior instead of a reading of `v1.0.11`.

### §7.3 — Structured errors

What the downloads page needs, and whether `v1.0.11` can tell it apart:

| Kind | `v1.0.11` source | Distinguishable today? |
|---|---|---|
| `notEnoughSpace` | `DownloadError::NotEnoughFreeSpace` (and Proton's equivalent) | Yes, but with no numbers. Upstream: "The free-space check discards its own error detail". |
| `sessionExpired` | `AuthError::NotAuthenticated`, `AuthError::TokenExpired` | Partly. A revoked refresh token comes back as `AuthError::ClientError { inner: String }`. Upstream: "A dead refresh token and a routine expiry both surface as the same opaque, unstructured error". |
| `network` | `ClientError::NetworkError`, `ClientError::MaxRetriesReached` | Yes. Timeouts from Phase 2 land here. |
| `notFound` | `DownloadError::BuildNotFound`, `ClientError::HttpError { status: 404 }` | Yes (by status). |
| `integrity` | `DownloadError::ChunkHashMismatch`, `ChunkIntegrityCheckFailed`, `DeflateError` | Yes. |
| `fileSystem` | `DownloadError::FileAllocationError`, `FileSystemError`, `CouldNotResolveFreeSpace`, `ProtonError::Io`, `SavesError::Io` | Only as one kind. `FileSystemError` is crate-private, so which failure it was is only in the message. Upstream: "Types a consumer must be able to name are not exported". |
| `cloudSavesUnsupported` | `SavesError::CloudStorageNotSupported` | Yes. |
| `cancelled` | The bridge's own (Phase 4) | n/a |

Ask upstream for: a status-aware auth error (revoked vs expired), required/available bytes on
`NotEnoughFreeSpace`, and exporting `FileSystemError`. Also "The four saves methods return
`SavesError`, not `GogDlError`", which the bridge's `SavesError` variant works around (collapsing
it is ROADMAP `v1.7.0`, not here).

### §7.4 — Free-space query

`PathResolver::get_free_space` exists but `mod fs` is private. Ask for
`GogDl::get_free_space(path) -> Result<u64, GogDlError>`, so the number Lumen shows is the same one
the download's own check compares against. Also check (and report upstream if confirmed) that its
disk lookup picks the **longest** matching mount point. It takes the first disk whose mount point
is a prefix of the path (`src/fs/path_resolver.rs:47-50`), so `/` can match before `/home`,
depending on `sysinfo`'s list order.

### §7.6 (part) — Save truncation

Upstream's "`download_save_files` truncates a good local save before it has the new one on disk".
A cancel or a listener-gone stop mid-write makes this data loss much easier to hit. Until it's fixed
upstream, the bridge never drops a saves future early.

### New §7.10 — Depot sizes per product

`get_install_size` can be computed today from `get_product_bundles`: sum `size()` (on disk) and
the chunks' `compressed_size` (download) per `ProductBundle.product_id`. That fetches every
product's full depot manifest. The build metadata already has per-depot `size`/`compressed_size`
and `productId` (`depot/build_metadata.rs`'s `Depot`), but nothing public exposes it. Ask for a
cheap per-product size query (or for `Depot` to be exposed from the build). This is a
nice-to-have; add it to GAPS §7 as item 10.

## Phase 1 — Stop a job when its listener goes away

GAPS §1 "Cancelling a stream on the Dart side doesn't stop the job". Not breaking.

- [ ] **Check first:** does cancelling a Dart subscription to an frb stream make the next
  `sink.add` fail? Write a throwaway test (or use the example app): start a Proton download,
  cancel the subscription, and log `sink.add`'s result. If it never fails, this phase is moot,
  Phase 4's cancel handle is the only way to stop a job, and GAPS §1 is closed by Phase 4 instead.
  Write down the result either way.
- [ ] If it fails: have `progress::drive`'s `emit` return whether the listener is still there, and
  have `drive` return early when it isn't. Each job then `select!`s its `gogdl-lib` future against
  the drive future ending early, and drops the job future. Keep the "events flush before
  `Finished`" order when nothing was cancelled.
- [ ] Saves jobs (`download_save_files`, `upload_save_files`) keep running to completion with no
  listener (see §7.6 above). Say so in a comment that points at the upstream item.
- [ ] Tests: `drive` stops on a closed emit, and a job future is dropped (observed through a
  drop guard in a fake future) when the listener goes away, with `tokio::time::pause`.

**Done when:** a cancelled subscription stops a download, repair, verify or Proton download within
one tick (checked in the example app or Lumen), and saves jobs still complete.

## Phase 2 — Request timeouts

GAPS §1 "Requests have no timeouts". Not breaking.

- [ ] Build the client with `Client::builder()` in `GogdlApi::new`: a `connect_timeout` (10s) and a
  `read_timeout` (30s, per read, so a stalled stream fails without capping a 500MB Proton tarball).
  **Not** an overall `timeout`, which would kill long transfers.
- [ ] Check that a timeout surfaces as `ClientError::NetworkError` and goes through `gogdl-lib`'s
  retry loop (six attempts with backoff), so one stall doesn't fail a download.
- [ ] `GogdlApi::new` stays `#[frb(sync)]` and infallible. If `builder().build()` can fail, fall
  back to `Client::new()` rather than panicking.

**Done when:** a request to a black-holed address fails within the timeouts instead of hanging
(check with a local listener that accepts and never answers).

## Phase 3 — Error kinds

GAPS §2 "Structured errors" (the downloads page part). Additive to `GogError`, but Phase 4 adds
`cancelled`, so it's released as part of the breaking change.

- [ ] Add a flat, non-opaque `GogErrorKind` enum (frb generates a Dart enum) with the kinds from the
  §7.3 table: `sessionExpired`, `network`, `notFound`, `notEnoughSpace`, `integrity`, `fileSystem`,
  `cloudSavesUnsupported`, `cancelled`, `unknown`.
- [ ] `GogError::kind() -> GogErrorKind`, `#[frb(sync)]`, next to `message()`. The mapping walks the
  nested `gogdl-lib` enums (for example, `GogDlError::DownloadError(DownloadError::ClientError(
  ClientError::AuthError(TokenExpired)))` is `sessionExpired`). Anything not in the table is
  `unknown`.
- [ ] Add `GogError::Cancelled`, a bridge-own variant for Phase 4, with a plain message.
- [ ] Unit tests: one per kind, built from constructed `gogdl-lib` errors, plus a catch-all test
  that an unmapped variant is `unknown`.
- [ ] Doc comment on `kind()`: which kinds are coarse until upstream §7.3 (revoked sessions show as
  `unknown`, `fileSystem` hides which failure it was, `notEnoughSpace` has no numbers).

**Done when:** every row of the §7.3 table has a test, and codegen shows `GogErrorKind` in Dart.

## Phase 4 — Cancel handle

GAPS §2 "Cancel and pause". **Breaking.** On the bridge, pause and cancel are the same thing: stop
the job and leave its files. Resume is `repair_game` (Phase 5). Deleting files on cancel is Lumen's
job.

- [ ] **Decide (your call):** how Dart gets a handle, given that frb stream methods already return
  the `Stream`.
  - (a) **Recommended.** Dart creates an opaque `JobHandle` (`#[frb(opaque)]`, `JobHandle::new()`
    sync) and passes it to the job method. `handle.cancel()` is sync and idempotent. Wraps a
    `tokio_util::sync::CancellationToken` (a new, small dependency) or a `watch` channel.
  - (b) A `job_id: String` argument and `GogdlApi::cancel(job_id)`, with a map of tokens on
    `GogdlApi`. More bookkeeping (map cleanup when a job ends) for no gain.
- [ ] Add the handle argument to `download_game`, `repair_game`, `verify_download` and
  `download_proton_release`. Each job `select!`s its future against `handle.cancelled()`. On cancel,
  drop the job future, let `drive` flush what it has, don't send `Finished`, and return
  `Err(GogError::Cancelled)`. Lumen's `guardBridgeStream` then delivers `cancelled` in-band.
- [ ] Saves jobs get no handle (see §7.6). Say so in their doc comments.
- [ ] A cancel that races a finished job is a no-op: the job returns its own result.
- [ ] Doc comments on each job: cancelling leaves resumable state for game jobs (call
  `repair_game`), and a partial tree under `path` for Proton (see §7.2).
- [ ] Tests: cancel before start, mid-job and after finish, using fake job futures and
  `tokio::time::pause`. Check no `Finished` after a cancel, and `kind() == cancelled`.
- [ ] If Phase 1 found that `sink.add` never fails, tick GAPS §1 "Cancelling a stream…" here, since
  the handle is now the way to stop a job.

**Done when:** in the example app or Lumen, cancelling a download stops network and disk activity
within a tick, and `repair_game` on the same path completes the install.

## Phase 5 — Resume path

GAPS §2 "Resume an interrupted install". Not breaking.

- [ ] **Decide (your call):**
  - (a) **Recommended.** Document it only. `download_game`'s and `repair_game`'s Dart doc comments
    say that `repair_game` resumes an interrupted or cancelled install and `download_game` always
    starts over (from upstream's rustdoc).
  - (b) Also add `resume_download` as an alias of `repair_game`. It makes Lumen's call site read
    better, at the cost of a second name for one job.
- [ ] Mention the performance caveat (upstream's `repair` checksums freshly allocated chunks), so
  Lumen's resume progress isn't a surprise.

**Done when:** the generated Dart API documents the resume path.

## Phase 6 — Install size and free space

GAPS §2 "Install and download size before installing" and "Free space at the install path". Not
breaking.

- [ ] `get_install_size(game_id, build_name, products) -> InstallSize` with `download_bytes`
  (compressed), `disk_bytes` (uncompressed) and `products: Vec<ProductSize>` (`id`,
  `download_bytes`, `disk_bytes`), summed from `get_product_bundles` by `product_id` (parse the
  string id to `i32`). Use the same sums as `download_game`'s and `verify_download`'s totals, and
  share the helper so they can't drift.
- [ ] `get_free_space(path) -> u64`. Upstream §7.4 isn't public, so implement it here: `statvfs`
  (through `nix` or `rustix`) on the nearest existing ancestor of `path`, since the install
  directory usually doesn't exist yet. Return the space available to the user (`f_bavail`), and
  check against `sysinfo`'s `available_space` (what upstream compares against) that both give the
  same number for the same mount.
- [ ] Doc comment: the download's own check compares `disk_bytes` against free space, and a game
  already partly on disk needs less than `disk_bytes`. Lumen's check is a warning, not a guarantee.
- [ ] Tests: the size sums from a JSON fixture, and `get_free_space` on the temp dir and on a
  missing child of it.

**Done when:** Lumen's install dialog can show download and disk size per product and the free
space at the chosen path.

## Patches

Only if upstream ships one of the requests before Lumen `v1.3.0` is done. Each is one small
session and one tag, with the same release steps as `v1.2.x`: bump both versions and both lock
files, tick the GAPS item, add a `CHANGELOG.md` section, commit ("v1.3.x: …"), tag on the branch,
green tag pipeline.

- **`gogdl-lib` bump with the cancellation contract (§7.2):** replace the "from reading the code"
  notes in the job doc comments with the upstream contract, or switch to upstream's
  `CancellationToken` if that's what it ships. Enable cancel for saves jobs once §7.6's truncation
  fix is in the same bump.
- **`gogdl-lib` bump with structured errors (§7.3):** map the new variants (revoked session,
  free-space numbers, filesystem failure), which shrinks `unknown`. Adding fields to a kind (for
  example required/available bytes) is additive in Dart; changing the enum's shape is not, and
  waits for `v1.5.0`.
- **`gogdl-lib` bump with a public free-space query (§7.4):** replace the bridge's `statvfs` with
  it, so both checks agree by construction.

Anything upstream ships after Lumen `v1.3.0` goes to ROADMAP `v1.7.0` instead.
