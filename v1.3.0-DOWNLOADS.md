# v1.3.0 — Download management

Work plan for the `v1.3.0` entry in [ROADMAP.md](ROADMAP.md). The goal is everything Lumen's
`v1.3.0` download management stage needs from the bridge: stopping and cancelling jobs, the resume
path, error kinds Dart can switch on, install size and free space, and request timeouts. It's a
**breaking** release: job methods take a cancel handle and errors carry a kind, so it ships together
with the Lumen change that adopts it, and it's tagged **before** Lumen starts its `v1.3.0`.

GAPS items closed by `v1.3.0`: §1 (cancelling a stream doesn't stop the job, no request timeouts),
§2 (cancel and pause, structured errors for the downloads page, install and download size, free
space, resume an interrupted install). The login error kinds in §2 "Structured errors" stay open
for `v1.5.0`.

This release depends on `gogdl-lib` more than `v1.2.0` did. **Dependencies on `gogdl-lib`** lists
what's needed upstream, whether `gogdl-lib` `v1.2.3` ships it, and which bridge phase each one
affects. Upstream shipped nearly all of it in `v1.2.0`–`v1.2.3`, so Phase 0 moves the pin to
`v1.2.3` and the phases use the upstream API. The one open item (revoked vs expired sessions) has a
fallback and doesn't block the release.

Tick each checkbox as it's done, one commit per phase (or smaller).

## Branch

All work happens on a new branch, created from `main` before Phase 0:

```sh
git switch main
git pull
git switch -c feat/v1.3.0-downloads
```

- Commit per phase (or smaller). Don't commit to `main` directly.
- Push the branch to `origin` and run the pipeline manually on it after each phase.
- Every tag (`v1.3.0`, and any `v1.3.x` under **Patches**) goes on a `feat/v1.3.0-downloads`
  commit, as in `v1.2.0`. Tag pipelines run from the tag, so CI/CD and Lumen's pin don't need
  `main`.
- After the last tag (see **After `v1.3.0`**), merge into `main` with `git merge --ff-only`.

## Starting point

- `main` is at `e97fd98`. `pubspec.yaml` and `rust/Cargo.toml` are at `1.2.4`. Flutter `3.47.2`
  (`.fvmrc`), frb `2.13.0`, Rust `1.98.1` (`rust/rust-toolchain.toml`).
- `gogdl-lib` was pinned to `v1.0.11`. Phase 0 moved the pin to `v1.2.3` (see **Dependencies on
  `gogdl-lib`**).
- `rust/src/api/gogdl.rs` is ~370 lines. The six jobs (`download_game`, `repair_game`,
  `verify_download`, `download_proton_release`, `download_save_files`, `upload_save_files`) each
  `tokio::join!` the `gogdl-lib` future with `progress::drive` and discard every `sink.add`
  result (`let _ = ...`).
- `GogError` is an opaque enum with two variants (`GogdlError(GogDlError)`,
  `SavesError(SavesError)`) and a single `message()`. Lumen matches on nothing: it shows
  `gogErrorText()` (`lumen/lib/common/gog_error.dart`).
- A job's `Result` doesn't reach Dart in-band. frb discards it for stream methods, and Lumen's
  `guardBridgeStream` (`lumen/lib/state/bridge_stream.dart`) catches it in a zone and re-injects it
  into the stream. A cancelled job's outcome goes through the same path.
- `GogdlApi::new` builds `Client::new()`, with no timeouts.
- `frb`'s `StreamSink::add` returns `Err(Rust2DartSendError)` only when posting to the Dart port
  fails. Whether cancelling the Dart subscription closes that port is **unverified** (Phase 1
  checks it first).

### Moving the pin to `v1.2.3`

The bump is **breaking** for the bridge's build, not only additive. It fits here, since `v1.3.0` is
a breaking release anyway.

- `v1.2.0` makes the eight event enums, `FileSystemError`, `DownloadError`, `ProtonError` and
  `SavesError` `#[non_exhaustive]`. Every `match` on them in `rust/src/progress/` (`download.rs`,
  `repair.rs`, `verify.rs`, `proton.rs`, `install.rs`, and the saves trackers) needs a `_ =>` arm.
- `v1.2.0` gives `NotEnoughFreeSpace` `{ required, available }` and `CouldNotResolveFreeSpace`
  `{ path }`, in both `DownloadError` and `ProtonError`.
- `v1.2.3` deprecates `DownloadEvent::Preparing` and `Prepared` (still sent, removed in `v1.4.0`).
  The matches in `progress/download.rs` and `progress/repair.rs` (and `repair.rs`'s test helper)
  need `#[allow(deprecated)]` or a move to `Started`, or `cargo clippy -D warnings` fails. Moving to
  `Started` is better, since `Preparing` goes away in the pin after this.
- Behavior changes picked up on the way, none needing bridge code: token-exchange errors no longer
  carry refresh tokens (`v1.1.1`), a refreshed expiry margin (`v1.1.2`), an unauthenticated 401 no
  longer loops (`v1.1.3`), an unowned product fails at once instead of retrying (`v1.2.0`),
  `repair_game` skips checksumming freshly allocated chunks (`v1.2.1`). `CHANGELOG.md` for `v1.3.0`
  should list them for Lumen.

### §7.2 — Cooperative cancellation ✅

Met in `v1.2.0`. `download_game`, `repair_game`, `verify_files`, `download_proton_release`,
`download_save_files` and `upload_save_files` each have a `# Cancelling` rustdoc section: dropping
the future stops the work, and `repair_game` completes an install whose download was dropped
(tested upstream). Upstream chose the drop contract, not a `CancellationToken`, so the bridge
cancels by dropping the job future (Phases 1 and 4).

- Game download and repair: a drop leaves partially written chunks, which `repair_game` catches and
  re-downloads.
- Proton: extraction goes into a hidden `.gogdl-staging-<tag>-<random>` directory under `path`,
  then replaces `path/<tag>` wholesale. A drop leaves `path` as it was, and staging directories left
  by a crashed run are removed by the next download into the same `path`. Lumen no longer has to
  clean up after a cancelled Proton download.
- Saves: see §7.6. Both saves jobs are now safe to drop.

### §7.3 — Structured errors ⚠️

What the downloads page needs, and whether `v1.2.3` can tell it apart:

| Kind | `v1.2.3` source | Distinguishable? |
|---|---|---|
| `notEnoughSpace` | `DownloadError::NotEnoughFreeSpace { required, available }` (and Proton's) | ✅ Yes, with the numbers (`v1.2.0`). |
| `sessionExpired` | `AuthError::NotAuthenticated`, `AuthError::TokenExpired` | ❌ **Partly.** A revoked refresh token is still `AuthError::ClientError { inner: String }`. |
| `network` | `ClientError::NetworkError`, `ClientError::MaxRetriesReached` | ✅ Yes. Timeouts from Phase 2 land here. |
| `notFound` | `DownloadError::BuildNotFound`, `ClientError::HttpError { status: 404 }` | ✅ Yes (by status). |
| `integrity` | `DownloadError::ChunkHashMismatch`, `ChunkIntegrityCheckFailed`, `DeflateError` | ✅ Yes. |
| `fileSystem` | `DownloadError::FileAllocationError`, `FileSystemError`, `CouldNotResolveFreeSpace { path }`, `ProtonError::Io`, `SavesError::Io` | ✅ Yes. `FileSystemError` is exported (`v1.2.0`), so the bridge can name which failure it was. |
| `cloudSavesUnsupported` | `SavesError::CloudStorageNotSupported` | ✅ Yes. |
| ~~`cancelled`~~ | Dropped in Phase 4: a cancel is an in-band `Cancelled` event, not an error | n/a |

**Not met:** upstream's "A dead refresh token and a routine expiry both surface as the same
opaque, unstructured error" is still open. Upstream's ROADMAP puts it in its `v1.5.0` ("Login error
kinds (§7.3 auth part)"), which lines up with this repo's `v1.5.0` login kinds. Until then, a
revoked session maps to `unknown` (or to `sessionExpired` only when it's
`NotAuthenticated`/`TokenExpired`), and Phase 3's doc comment says so. It doesn't block `v1.3.0`.

Also still open upstream, and not needed here: "The four saves methods return `SavesError`, not
`GogDlError`" (the bridge's `SavesError` variant works around it; collapsing it is ROADMAP
`v1.7.0`).

### §7.4 — Free-space query ✅

Met in `v1.1.6`: `GogDl::get_free_space(&self, path: &Path) -> Result<u64, GogDlError>`, the same
figure the download, repair and Proton checks compare against. `path` needn't exist. The disk
lookup now picks the **longest** matching mount point (a behavior change: the check can fail where
it used to pass). The bridge uses it directly (Phase 6), with no `statvfs`.

### §7.6 (part) — Save truncation ✅

Met in `v1.2.0`. `download_save_files` writes a sibling `.<name>.gogdl-part` file, syncs it and
renames it over the destination, and that write finishes even if the future is dropped: the old
save or the complete new one, never a partial one. `upload_save_files` only reads local files, so a
drop leaves them untouched (the file in flight may or may not be stored, so upload again to be
sure). The saves jobs no longer need excluding from cancel or the listener-gone stop.

### New §7.10 — Depot sizes per product ✅

Met in `v1.2.0`: `GogDl::get_product_sizes(game_id, build_name)` returns a `ProductSize {
product_id, size, compressed_size }` per product, from the build metadata, after the download's
language filter, with no manifest fetches. It equals what `get_product_bundles` sums. Add §7.10 to
this repo's GAPS §7 as already fixed upstream.

### Compressed download total ✅

Met in `v1.2.3`: `DownloadEvent::Started { compressed_total }`, sent once per download stage after
`Prepared`. `DownloadGameProgress.Started`'s total can come from it (for `repair_game`, only the
missing units), and the stage's `Progress` deltas minus `ProgressRegression` add up to it.

### Not a dependency, but relevant

- Upstream's "`download` re-downloads every chunk regardless of what's already correct on disk" is
  deferred to upstream `v1.3.0` (it adds a `VerificationStage` to `download_game`'s events). Until
  then `repair_game` stays the only resume path (Phase 5), and picking it up is a later bridge bump
  (ROADMAP `v1.7.0`).
- `DownloadEvent::Preparing`/`Prepared` are removed in upstream `v1.4.0`.

## Phase 1 — Stop a job when its listener goes away

GAPS §1 "Cancelling a stream on the Dart side doesn't stop the job". Not breaking.

- [x] **Check first:** does cancelling a Dart subscription to an frb stream make the next
  `sink.add` fail? Write a throwaway test (or use the example app): start a Proton download,
  cancel the subscription, and log `sink.add`'s result. If it never fails, this phase is moot,
  Phase 4's cancel handle is the only way to stop a job, and GAPS §1 is closed by Phase 4 instead.
  Write down the result either way.
  **From Lumen's plan:** Lumen's Phase 0 confirmed at runtime that cancelling the Dart
  subscription doesn't stop the job (the install dir was still growing 4 minutes later). That's
  consistent with `sink.add` errors being swallowed by `let _ =`, but it doesn't show whether they
  happen, so this check still stands.
  **Result: it fails.** A throwaway Linux integration test started a Proton download and
  cancelled the subscription after the third event. The next `sink.add` and every one after it
  returned `Err` (68 failures over the next 8s), and the job kept running. This matches frb
  2.13.0's code: the Dart `RustStreamSink` closes its `ReceivePort` in the `async*` generator's
  `finally` when the subscription is cancelled, and `Dart_PostCObject` to a closed port returns
  `false`.
- [x] If it fails: have `progress::drive`'s `emit` return whether the listener is still there, and
  have `drive` return early when it isn't. Each job then `select!`s its `gogdl-lib` future against
  the drive future ending early, and drops the job future. Keep the "events flush before
  `Finished`" order when nothing was cancelled.
  Done as `progress::run(job, translator, rx, emit) -> Option<Output>`, which all six jobs use.
  `None` means the listener went away and the job future was dropped, and the job returns
  `Ok(())` (there's nobody to report to; Phase 4 kept that). A failed final flush after the
  job has finished keeps its result. `download_game`, `repair_game` and `verify_download` also
  return before building the job future if the up-front `Started` add fails. The stop is noticed
  on the next emit, so a job that reports nothing (a stalled request) runs until it does. Phase
  2's read timeout bounds that, and Phase 4's handle doesn't depend on it.
- [x] Saves jobs (`download_save_files`, `upload_save_files`) stop the same way. Since `gogdl-lib`

  leaves local files untouched (see §7.6 above).
- [x] Tests: `drive` stops on a closed emit, and a job future is dropped (observed through a

## Phase 2 — Request timeouts

GAPS §1 "Requests have no timeouts". Not breaking.

- [x] Build the client with `Client::builder()` in `GogdlApi::new`: a `connect_timeout` (10s) and a
  `read_timeout` (30s, per read, so a stalled stream fails without capping a 500MB Proton tarball).
  **Not** an overall `timeout`, which would kill long transfers.
  Done in `rust/src/client.rs` (`client::build`), outside `api/` so frb doesn't list it.
- [x] Check that a timeout surfaces as `ClientError::NetworkError` and goes through `gogdl-lib`'s
  retry loop (six attempts with backoff), so one stall doesn't fail a download.
  **Result: only partly.** A timeout is a `reqwest::Error`, so it's always `NetworkError`. But only
  `HttpClient::fetch` (metadata, secure links) and game chunk downloads (`engine.rs`) retry it, so
  one stall doesn't fail a game download or repair. The Proton tarball (`stream_chunk`), saves
  download (`stream_chunk_with_headers`), saves upload (`put_stream`) and `login_with_code`
  (`post_token`) fail on the first timeout. That's still better than hanging. Requested upstream as
  GAPS §7.11.
- [x] `GogdlApi::new` stays `#[frb(sync)]` and infallible. If `builder().build()` can fail, fall
  back to `Client::new()` rather than panicking.
- **Found on the way: the read timeout bounds uploads.** reqwest 0.13 starts `read_timeout` at
  `send()` and only restarts it on reads of the response body, so it runs through the whole
  request-body upload. A save file whose upload takes more than 30s fails (about 4 MB on a 1 Mbit
  uplink). Decided: keep 30s, document it on `upload_save_files`, and ask upstream (GAPS §7.11). A
  test pins it down.
- Phase 7's `CHANGELOG.md` should say: requests now time out (10s connect, 30s without reading).
  Proton downloads, saves transfers and login fail on a timeout, and a save upload must finish
  within 30s per file.

**Done when:** a request to a black-holed address fails within the timeouts instead of hanging
(check with a local listener that accepts and never answers).
Checked by `client.rs`'s tests, on loopback with 200ms timeouts: a server that never answers, a body

## Phase 4 — Cancel handle

GAPS §2 "Cancel and pause". **Breaking.** On the bridge, pause and cancel are the same thing: stop
the job and leave its files. Resume is `repair_game` (Phase 5). Deleting files on cancel is Lumen's
job.

- [x] **Decide (your call):** how Dart gets a handle, given that frb stream methods already return
  the `Stream`.
  - (a) **Recommended.** Dart creates an opaque `JobHandle` (`#[frb(opaque)]`, `JobHandle::new()`
    sync) and passes it to the job method. `handle.cancel()` is sync and idempotent. Wraps a
    `tokio_util::sync::CancellationToken` (a new, small dependency) or a `watch` channel.
  - (b) A `job_id: String` argument and `GogdlApi::cancel(job_id)`, with a map of tokens on
    `GogdlApi`. More bookkeeping (map cleanup when a job ends) for no gain.
  - **From Lumen's plan:** Lumen's D1 calls it `CancelToken`. Pick one name and tell Lumen.
  **Decided: (a), named `CancelToken`** (Lumen's name), wrapping `tokio_util`'s
  `CancellationToken` (`tokio-util` was already locked at `0.7.19` through a transitive
  dependency). In `rust/src/api/cancel_token.rs`. The job methods take `cancel: &CancelToken`,
  which frb decodes with a shared read lock, so a sync `cancel()` during the job isn't blocked.
- [x] **Decide (your call), from Lumen's plan:** how a cancel reaches Dart. Lumen's D2 asks for a
  terminal `Cancelled` variant on each progress union, emitted once, then `Ok(())`, not an error.
  This plan returns `Err(GogError::Cancelled)`. Lumen's reason (an opaque `GogError` could only be
  matched by string) goes away with Phase 3's `kind()`. The in-band variant still makes Lumen's
  exhaustive `switch`es fail to compile until they handle cancel, and it keeps cancels off
  `guardBridgeStream`'s error path. Settle this before writing the job changes.
  **Decided: Lumen's D2, on all six progress enums.** On a cancel, `drive` flushes what it has,
  `Cancelled` goes out last, and the method returns `Ok(())`. Nothing produces
  `GogError::Cancelled` or `GogErrorKind::Cancelled` any more, so both are removed (unreleased,
  and a dead case would only confuse Lumen's `switch`es).
- **From Lumen's plan:** a cancel while `get_product_bundles` (or any pre-job fetch) is still
  running must also end as cancelled and write nothing to disk, so the `select!` covers the whole
  method body, not just the `gogdl-lib` job future. Lumen also asks that nothing is sent after
  `Cancelled`. That conflicts with "let `drive` flush what it has" below, so if the in-band variant
  wins, flush first and send `Cancelled` last.
- [x] Add the handle argument to `download_game`, `repair_game`, `verify_download`,
  `download_proton_release`, `download_save_files` and `upload_save_files`. Each job `select!`s its future against `handle.cancelled()`. On cancel,
  drop the job future, let `drive` flush what it has, don't send `Finished`, and return
  `Err(GogError::Cancelled)`. Lumen's `guardBridgeStream` then delivers `cancelled` in-band.
  Done, with D2's ending instead (`Cancelled`, then `Ok(())`). The pre-job fetches
  (`get_product_bundles`, `get_proton_release_by_tag`) run under `run_until_cancelled`, and
  `progress::run` takes the token and returns `Outcome::{Finished, Cancelled, ListenerGone}`. It
  boxes the job so a cancel can drop it while `drive` still drains. On a cancel, `drive` closes
  `rx` instead of waiting for every sender to drop, since Proton's extraction task (a
  `spawn_blocking`) holds a sender for a while after its job future is dropped. A job that's
  already cancelled is never polled.
- [x] A cancel that races a finished job is a no-op: the job returns its own result.
  `run`'s `select!` is biased towards the job's output, like `run_until_cancelled`.
- [x] Doc comments on each job, from upstream's `# Cancelling` sections: cancelling leaves
  resumable state for game jobs (call `repair_game`), leaves `path` as it was for Proton, keeps the
