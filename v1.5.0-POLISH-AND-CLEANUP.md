# v1.5.0 — Polish and API cleanup

Work plan for the `v1.5.0` entry in [ROADMAP.md](ROADMAP.md) and its `v1.5.1` patch. The goal is
what Lumen's `v1.5.0` work plan (`../lumen/v1.5.0-POLISH-AND-PACKAGING.md`, "Dependency changes" and
Phase 6) asks the bridge for: login error kinds (its D1) and the breaking cleanup (its D3). Its D2, a
precompiled `.so`, was **dropped by Lumen's Phase 0** (it ships an AppImage built from source in its
CI image), so it's out of this release. This is a **breaking** minor: Lumen adopts it in its Phase 7,
on one branch, working from this release's `CHANGELOG.md` entry.

GAPS items closed by `v1.5.0`: §2 "Structured errors" (the login kinds, its last open part), §3
"Progress enums mix positional and named fields", "`ProtonDownloadProgress::Extracted` is lossy and
undocumented", "`GameBuild` carries the release date twice", "`DownloadableProduct.product_type` is
a free-form string" and "`GogError` has a separate `SavesError` variant". The `v1.5.1` patch closes
§5 "Progress channels are unbounded".

The steps are short, and several share one MR: **5 MRs** in all. Inside an MR, each step is one
commit on the branch, and the squash leaves one commit on `main` (titled as the MR). Manual checks
make no commit. Tick each checkbox as it's done.

## Workflow

`main` and the `v*` tags are protected (README "CI and releases"):

- Every MR is opened with **push options**, never `glab` or the web UI's "New merge request":

  ```sh
  git push -u origin <branch> \
    -o merge_request.create \
    -o merge_request.target=main \
    -o "merge_request.title=<title from the table>" \
    -o merge_request.remove_source_branch
  ```

  Later pushes to the same branch are a plain `git push`. Push options don't fill the description
  from `.gitlab/merge_request_templates/Default.md`: paste the template's checklist into the MR and
  tick it there. Check the title and squash message in the merge widget before merging.
- Open the MR on the branch's first push, so its pipeline runs on every later push (a branch without
  an MR runs nothing).
- Every MR: the gates in `README.md` "Development" pass locally, the MR pipeline is green.
- MR 2 makes `main` Dart-breaking before any tag carries it. That's fine, since Lumen pins tags.
  Until `v1.5.0` is tagged, a `v1.4.x` hotfix branches from the `v1.4.3` tag, not `main`.
- Tags only go on `main`, after a `release/vX.Y.Z` MR merges. Lumen pins the bridge from its GitHub
  mirror, so a tag isn't done until the mirror has it.
- If Lumen's Phase 7 wants to start before the tag, its `feat/v1.5.0-bridge` points `ref:` at MR 2's
  merged commit on `main`, and must be back on a tag before its Phase 7 commit (Lumen's own rule).

  are internal and change no signature, error or event.
- Upstream's devlog (`../gogdl-lib/devlog/v1.4.0-errors-and-cleanup.md`, "Downstream breaks") lists
  what the bump breaks here: 13 errors in `rust/src/error_kind.rs` (the dead `NetworkError`/`Http`
  arms and the tests that build them, `FileCreationError`, `AuthError::ClientError`, and E0004 on the
  `GogDlError` match, which needs a `_` arm and a `SavesError` arm), four in
  `progress/{download,repair}.rs` (tests that emit `Preparing`/`Prepared`), and the `repair_game` call
  in `api/gogdl.rs` under `clippy -D warnings`.
- What GOG answers (upstream's step 1): a bad and an expired login code are both
  `400 invalid_grant` on the `authorization_code` grant, now `AuthError::InvalidLoginCode`; a dead
  refresh token is `invalid_grant` on `refresh_token`, now `AuthError::SessionRevoked`, which every
  authenticated method returns. A network failure is `AuthError::NetworkError`.
- Lumen pins `v1.4.3` and has finished its Phases 0–5, including Phase 4 (off the deprecated getters),
  so removing them breaks nothing it still calls. It still calls `repairGame` (`gogdl_backend.dart`),
  and has 28 `field0`/`field1` uses in `downloads_state.dart` and `proton_state.dart`.
- Stale text found by Lumen's Phase 0: GAPS §7.3 says upstream plans the login kinds for its
  `v1.5.0` and the saves errors for this repo's `v1.7.0`; `GogError::kind()`'s doc comment says a
  revoked session is `unknown` until upstream's `v1.5.0`. Upstream shipped both in `v1.4.0`.

## Decisions

Recommended answers in italics. Change them here before the step that needs them.

- [x] **D1. A revoked session's kind** (Step 4). (a) *Map `SessionRevoked` onto the existing
      `sessionExpired`.* Lumen reacts the same way to both (sign in again), its `jobErrorText` already
      has the case, and `message()` keeps GOG's description. Only `invalidLoginCode` is new.
      (b) A new `sessionRevoked` kind: one more case in every Lumen `switch` for no different
      behavior. Checked: Lumen's `jobErrorText` (`gog_error.dart`) already handles `sessionExpired`.
- [x] **D2. `repairGame`** (Step 2). Upstream deprecated `repair_game` (same pipeline as
      `download_game` since its `v1.3.0`, removed in its `v1.5.0`). (a) *The bridge's `repairGame`
      keeps its Dart signature and `RepairGameProgress`, and calls upstream's `download_game`* (same
      `DownloadStageEvent` sender, so `RepairTranslator` is unchanged). Not breaking, and not in
      Lumen's Phase 7. (b) Remove `repairGame` from Dart too: tidier, but it adds a migration Lumen's
      Phase 7 doesn't plan for. Revisit in `v1.6.0`, when upstream removes its method. Checked: upstream's
      `repair_game` is `self.downloader.download_game(bundles, path, tx)` with the same sender.
- [x] **D3. `ProductType`'s variants** (Step 7). Upstream's `productType` is upper case in real
      responses (`"GAME"`, `"DLC"`) and lower case in fixtures. (a) *`game`, `dlc` and `other`,
      compared case-insensitively*, so a pack or a new type doesn't fail the call. Lumen maps each variant to its own label (it shows
      `productType` as raw text today and filters on `== "GAME"`); `other` loses the raw string. (b) `game` and
      `dlc`, and drop anything else from the list: hides a product Lumen might want to show.
- [ ] **D4. `v1.5.1`'s outcome** (Step 12). Upstream's job methods take an `UnboundedSender`, so the
      first hop can't be bounded here. Counters are coalesced per 150 ms tick, but per-path events
      (verify/repair `ChecksumMismatch`, `FileNotFound`, `CouldNotResolvePath`) are emitted at once, so
      a badly corrupted install can queue one per bad chunk in the Dart port. If Step 12 shows the
      bridge's buffering is bounded for both, close GAPS §5 with the measurement, ship no tag, and fold the notes into
      MR 5. Only tag `v1.5.1` if something in the bridge changes.

## Notes

**Step 5** (2026-10-17, throwaway probe in `example/`, deleted):

- Truncated code: `invalidLoginCode`, "Code doesn't exist or is invalid for the client".
- The same code exchanged a second time right after the first: **accepted** (GOG has a grace window), so
  "exchanged once" isn't rejected at once. Retried ~10 min later: `invalidLoginCode`, "The authorization
  code has expired". A never-used code left 10+ minutes wasn't tested separately.
- Network off: `network`.
- Garbage refresh token, locally expired: `sessionExpired`, "Invalid refresh token, client_id:…".
- A real session refreshed once, then the original (pre-rotation) refresh token restored: still
  refreshes fine, so GOG doesn't invalidate rotated tokens at once.
- **Gap:** a garbage access token with `valid_until` in the future makes `getOwnedGames` fail with
  `unknown` ("Deserialization error"): `embed.gog.com/user/data/games` answers a bad bearer with a 302 to
  an HTML login page, not a 401, so upstream's refresh-on-401 never runs. It only matters when GOG kills
  an access token before `valid_until`. Candidate for GAPS §7 (upstream).
